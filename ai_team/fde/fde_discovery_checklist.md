# FDE Discovery Checklist

顧客・現場ヒアリングで確認する項目。skill-field-discovery / skill-stakeholder-mapping / skill-pain-point-analysis が使用する。全項目を埋めることが目的ではなく、**未確認項目を「未確認」と明示すること**が目的（想像で埋めることを禁止する）。

## 顧客背景

- [ ] 会社・部門・事業の概要と、今回の相談がどの事業判断に紐づくか
- [ ] 相談に至った直近のきっかけ（障害・監査・人員変動・経営指示など）
- [ ] 過去に類似の取り組みがあったか。あれば失敗/中断の理由

## 業務背景

- [ ] 対象業務の目的と、業務が生む成果物（帳票・報告・判断）
- [ ] 業務の頻度・季節性・締め日などの時間制約
- [ ] 業務量（件数/人数/時間）を数字で確認したか

## 表面的な要望

- [ ] 顧客の言葉のまま記録したか（言い換えない）
- [ ] 「何を作ってほしい」と「何に困っている」を分けて記録したか

## 本質課題

- [ ] 要望の背景にある業務課題を「なぜ」で2段以上掘ったか
- [ ] 課題を裏づける事実（実物・数字・事例）を確認したか
- [ ] problem_statement（解くべき課題1文）に合意できるか

## 利用者

- [ ] 実際に日常で使う人（役職でなく実務者）を特定したか
- [ ] 利用者のITリテラシーと業務習熟度
- [ ] 利用者が今のやり方を変えたい動機を持っているか

## 意思決定者

- [ ] 導入判断・予算判断を持つ人
- [ ] 判断者が重視する評価軸（コスト/リスク/スピード/実績）
- [ ] 判断のタイミング（稟議・期初予算など）

## 運用者

- [ ] 導入後に維持・運用する人（顧客側/セレス側）
- [ ] 運用者のスキル（SQL可否・ツール経験）
- [ ] 障害時に最初に連絡が来る人

## 現状業務フロー

- [ ] 開始トリガー〜完了までを実物（画面・帳票・ファイル）で確認したか
- [ ] 各ステップの担当・所要時間・使用システム
- [ ] 月次/日次などの実施タイミング

## 現場の痛み

- [ ] どのステップで、誰が、何に、どれだけ困っているか（数字で）
- [ ] 痛みの発生頻度と業務影響（遅延・ミス・残業・信頼低下）
- [ ] 現場が既に行っている回避策

## 手作業・属人化

- [ ] 手作業（転記・目視確認・手動実行）の箇所と所要時間
- [ ] 特定個人しかできない作業と、その人の不在時の扱い
- [ ] Excelマクロ・個人スクリプト等の「隠れ資産」の有無

## データ発生源

- [ ] データがどこで発生するか（システム入力/紙/メール/センサー等）
- [ ] 発生粒度・頻度・量（行数/日など概算）
- [ ] 発生源の品質問題（欠損・重複・コード体系の揺れ）

## 既存システム

- [ ] 対象業務が触れるシステム一覧（基幹/SaaS/Excel）
- [ ] 各システムのデータ取得手段（API/DB直接/CSV出力/画面のみ）
- [ ] 改修可否と管轄（顧客情シス/ベンダー/契約上の制約）

## 既存制約

- [ ] 予算・期間・体制の制約
- [ ] 業務ルール上の制約（締め処理・承認手続・監査要件）
- [ ] 技術制約（オンプレのみ・クラウド不可・接続時間帯制限など）

## セキュリティ・権限

- [ ] 扱うデータの機密区分（個人情報・原価・人事など）
- [ ] 誰が何を見てよいか（部門・役職での参照制御要否）
- [ ] 監査・ログ要件（内部統制・業界規制）
- [ ] 外部接続・データ持ち出しの制約

## 成功条件

- [ ] 顧客の言葉で「これができたら成功」を1文にしたか
- [ ] 定量指標に変換できるか（時間・件数・率）
- [ ] いつ時点で測るか（導入後1/3/6ヶ月）

## 受入条件

- [ ] 顧客が受け入れ判断に使う条件（検証方法とセット）
- [ ] 受入判断者と受入の場（立会い・報告会）

## 導入時の懸念

- [ ] 現場の抵抗・不安（仕事が奪われる/操作が難しい等）
- [ ] 並行運用期間の要否と負荷
- [ ] 教育・説明にかけられる時間

## 未決事項

- [ ] 未確認・未合意の項目を一覧化したか（判断者・期限・ブロック対象付き）

## 次に確認すること

- [ ] 次回ヒアリングで確認する項目と、確認方法（誰に・何を見せてもらうか）
- [ ] 顧客側の宿題と期限
