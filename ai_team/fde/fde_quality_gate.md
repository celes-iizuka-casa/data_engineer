# FDE Quality Gate

FDE成果物の品質ゲート。`../review/quality_gate.md` / `../review/professional_quality_gate.md` の共通ゲートに加えて、FDE案件で適用する成果物別チェック。判定は `../review/quality_scoring_rubric.md` の PASS / PASS_WITH_CONDITIONS / REWORK_REQUIRED / BLOCKED に接続する。

## 目的

- FDE成果物が「議事録・要約」で終わることを防ぎ、実装チームが動ける粒度を機械的に確認する
- 何でも屋化（責任外の断定・実装の抱え込み）を成果物レベルで検出する
- 導入・定着・効果測定の省略を検出する

## FDE成果物の品質基準

- 事実（実物・数字・出典）と推論・仮定が分離されている
- 未確認事項が「未確認」と明示されている（想像で埋めていない）
- 顧客要望の転記でなく、本質課題への変換がある
- 責任外領域（`fde_scope_boundary.md` の7領域）を断定していない
- 受け手（顧客/実装チーム/セレス）が次に動ける状態になっている

## Discovery品質チェック

- [ ] 表面的な要望と本質課題が分離され、本質課題に裏づけ事実がある
- [ ] 利用者・意思決定者・運用者が実名/実部門レベルで分離されている
- [ ] データ発生源・既存システム・制約が確認手段付きで記録されている
- [ ] セキュリティ・権限の確認項目が埋まっているか「未確認」明示
- [ ] 成功条件が顧客の言葉+定量指標候補で記録されている
- [ ] 未決事項と次に確認することが担当・期限付きである

## Business Flow品質チェック

- [ ] 現状フローが実物で裏づけられている（未確認ステップは明示）
- [ ] 各ステップに担当・所要時間・使用システムがある
- [ ] To-Beの各ステップに 自動/半自動/人間判断/廃止 のラベルがある
- [ ] 手作業・データ断絶・例外処理が洗い出されている
- [ ] ギャップが要件区分（機能/データ/運用/教育）へ変換されている

## MVP Scope品質チェック

- [ ] 検証仮説が1つに絞られている
- [ ] 含める/含めない/将来拡張の3区分が理由付きで明文化されている
- [ ] セキュリティ・運用・データ品質・テストの最低ラインが計画に入っている
- [ ] 成功条件・受入条件が測定/検証可能
- [ ] `fde_mvp_scoping_guide.md` のチェックリストに合格している

## Engineering Handoff品質チェック

- [ ] テンプレ29セクションが埋まっている（該当なしは理由付き）
- [ ] Role別依頼10種すべてに記載がある（依頼なしのRoleも「なし+理由」）
- [ ] 各依頼に 依頼内容/前提・制約/完了条件 がある
- [ ] 受入条件に検証方法と判定Roleがある
- [ ] 未決事項にブロック対象・判断者・期限がある
- [ ] 技術選定を断定していない（候補+制約+推奨に留まっている）
- [ ] 参照元（一次情報のパス）がある

## Adoption Plan品質チェック

- [ ] 定着責任者（顧客側）が特定されている
- [ ] 旧手順の廃止条件・時期がある
- [ ] 初回利用までの準備（権限・データ・案内）が担当付きである
- [ ] 定着リスクと対策が対になっている
- [ ] `fde_adoption_success_guide.md` の「作って終わりを防ぐチェックリスト」に合格

## Success Metrics品質チェック

- [ ] 業務指標が主指標になっている（技術指標のみは不可）
- [ ] ベースライン取得済み/取得計画がある
- [ ] 測定時期・方法・データ源・担当が決まっている
- [ ] 効果が出ない場合の判断基準がある

## Feedback Loop品質チェック

- [ ] フィードバックが出典付きで記録され、7分類に沿っている
- [ ] バグ/仕様変更/教育課題が混同されていない
- [ ] 優先順位に業務影響×頻度×利用者数の根拠がある
- [ ] Backlog項目に対応先Roleと受入条件の種がある
- [ ] 対応しない項目に理由がある

## Personalization反映チェック

- [ ] `../personalization_policy.md` のprofile解決順を確認した（Local profile不在時は匿名shared defaultを使い、個人属性を推測しない）
- [ ] 成果物の粒度・用語が利用者タイプ（`../personalization_policy.md`）に合っている
- [ ] 顧客向け説明がある場合、customer_explanation_template の型に沿い技術詳細が業務語に変換されている

## セキュリティ・運用・データ品質チェック

- [ ] 扱うデータの機密区分と参照制御要件が整理されている
- [ ] 運用の最低ライン（失敗検知・再実行・担当）がhandoffに含まれる
- [ ] データ要件に粒度・鮮度・保持期間・既知の品質問題がある
- [ ] 該当Role（Security/SRE/Data Engineer）への依頼が明示されている

## 不合格条件

以下のいずれかで REWORK_REQUIRED:

- 顧客要望の転記だけで本質課題の整理がない
- Role別依頼に空欄がある（なし+理由の明記漏れ）
- 検証方法のない受入条件 / ブロック対象のない未決事項
- 責任外領域（技術選定・セキュリティ・SRE等）の断定
- 導入・定着・成功指標の省略（省略理由の記録なし）
- 想像で埋めた現場事実（出典なしの断定）

以下は BLOCKED:

- セキュリティ・データ損失・復旧不能リスクの未整理のまま実装へ渡そうとしている
- 顧客の契約・法務判断が必要な事項をFDEが確定させている

## 差し戻し条件

- handoff後のQ&A往復が2回を超えた → handoff不備としてFDEへ差し戻し
- 受け手Roleが「着手不能」と判定 → 不足情報を特定してFDEへ差し戻し
- 差し戻し時は不足箇所・理由・期限を記録する（無言の差し戻し禁止）

## 完了条件

- 該当する成果物チェックすべてに合格（または例外理由・影響・代替統制・責任者・解消期限を記録）
- 共通ゲート（`../review/quality_gate.md`）に合格
- 必要性ゲート該当時（顧客提出物・本番・セキュリティ影響）はQuality Reviewerの独立レビュー完了
