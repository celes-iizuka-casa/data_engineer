# FDE Engineering Handoff Guide

FDEからTech Lead / 各Engineerへの引き継ぎガイド。skill-engineering-handoff が使用する。`../handoff_policy.md` のFDE経路の詳細版。

## 目的

Handoffは議事録の要約ではなく「実装チームの作業指示の材料」。受け手が追加説明なしで判断・着手できる状態を作る。FDE強化の最重要成果物であり、品質は `fde_quality_gate.md` のHandoff品質チェックで判定する。

## 引き継ぎが必要なタイミング

- MVPスコープ確定後・実装着手前（標準）
- PoC完了→商用化判断後
- 案件途中で責任外の最終判断が必要になったとき（部分handoff）
- 目安: handoff後のQ&A往復が2回を超えたらhandoff不備として差し戻し、FDEがhandoffを更新する

## Tech Leadへ渡す情報

- 必ず渡す: 業務背景 / 本質課題 / MVP・非スコープ / 現場制約（特に技術選定を縛るもの: オンプレ制約・既存資産・運用体制のスキル）/ solution_framingの候補案と推奨理由 / 未決事項とブロック対象
- 渡さなくてよい: ヒアリングの生ログ（参照元パスで足りる）
- よくある漏れ: 運用引き継ぎ先のスキルレベル（技術選定に直結する）

## Backend Engineerへ渡す情報

- 必ず渡す: 業務ルール / 利用者と権限 / API利用シーン / 例外ケースと業務上の扱い / 性能の業務要件（同時利用数・応答時間）
- よくある漏れ: 例外時に「業務では誰がどう直すか」（エラーハンドリング設計に直結）

## Frontend Engineerへ渡す情報

- 必ず渡す: 利用者のITリテラシー / 利用環境（端末・ブラウザ・現場の物理環境）/ 画面要件と業務上の優先度 / 既存画面・帳票の実物
- よくある漏れ: 現場の利用環境（工場の共有端末・手袋操作など）

## Data Engineerへ渡す情報

- 必ず渡す: データ発生源 / 粒度・主キー / 更新頻度・鮮度要件 / 保持期間 / 業務定義（「売上」の範囲など定義の揺れ）/ 既知の品質問題 / 利用者とアクセスパターン
- よくある漏れ: コード体系の揺れ・マスタ不整合（現場でしか分からない）

## Data Platform Engineerへ渡す情報

- 必ず渡す: 将来の利活用見込み（他部門展開・分析拡張）/ データガバナンス要件（PII・機密区分）/ 既存基盤の有無と管轄
- よくある漏れ: 「利活用未確定」の明示（基盤設計の分岐条件になる — `../../templates/development/sets/data_platform.md` の分岐規則参照）

## LLM Application Engineerへ渡す情報

- 必ず渡す: LLMで解きたい業務課題 / 入出力の実例（現場の実文書）/ 許容できる誤りの種類と率 / 誤り時の業務影響と人間確認の可否 / 機密データの制約
- よくある漏れ: 「間違えたらどうなるか」の業務影響（ガードレール・評価設計の前提）

## Integration Engineerへ渡す情報

- 必ず渡す: 連携先システムと管轄（情シス/外部ベンダー）/ 接続手段の現実性 / 連携先の変更予定・制約 / 相手先調整の窓口とリードタイム
- よくある漏れ: 相手先の検証環境提供時期（スケジュールを縛る）

## Security Engineerへ渡す情報

- 必ず渡す: データの機密区分 / 参照制御の業務要件（誰が何を見てよいか）/ 監査・規制要件 / 外部接続・持ち出し制約 / 顧客のセキュリティ審査プロセス
- よくある漏れ: 顧客側の内部統制・監査スケジュール

## QA Engineerへ渡す情報

- 必ず渡す: 受入条件（検証方法・判定Role付き）/ テスト正解データの所在（過去の手作業結果など）/ 現場テストの制約（本番データ利用可否・立会い要否）
- よくある漏れ: 「正解」が存在しない業務（正解データの作り方から合意が必要）

## SREへ渡す情報

- 必ず渡す: 業務上の停止許容時間 / 障害時の業務側の代替手段 / 運用者のスキルと体制 / 通知手段の制約（メールのみ等）/ 保守契約の範囲
- よくある漏れ: 「誰が夜間・休日に対応するか」（顧客側体制）

## Handoffに含めるべき情報

`../../templates/engineering_handoff_template.md` の29セクションを正とする: 概要 / 顧客・現場背景 / 解くべき課題 / 本質課題 / MVPスコープ / 非スコープ / 現状業務フロー / To-Be業務フロー / 機能・非機能・データ・API連携・画面・権限セキュリティ・運用の各要件 / 受入条件 / 成功指標 / 未決事項 / **Role別依頼10種**（Tech Lead / Backend / Frontend / Data / Data Platform / LLM App / Integration / Security / QA / SRE）/ 参照元。

## Handoffでやってはいけないこと

- 顧客要望の転記だけで「解くべき課題」「本質課題」を書かない
- 「依頼なし」のRoleを空欄にする（依頼なし+理由を明記する。空欄は検討漏れと区別できない）
- 検証方法のない受入条件を書く
- 未決事項にブロック対象（どの依頼が止まるか）を書かない
- 技術選定を先取りして断定する（Tech Leadの領分。候補と制約の提示に留める）
- 参照元（一次情報のパス）を省略する

## Handoff完了条件

- `fde_quality_gate.md` のEngineering Handoff品質チェックに合格している
- 受け手Role（またはPMO）が「追加説明なしで着手可能」と確認している
- 未決事項がブロック対象・判断者・期限付きで整理されている
- handoff後の実行環境切替（Claude Code→Codex）が `../model_effort_selection_policy.md` のFDE工程別表に従って記録されている
