# FDE MVP Scoping Guide

MVPスコープ切り出しのガイド。skill-mvp-scoping が使用し、`../workflows/mvp_scoping_workflow.md` の判断基準を補完する。

## 目的

- 最小で顧客価値が出る範囲を切り出し、過剰実装と検証遅延を防ぐ
- 「やらないこと」を明文化し、期待値のズレと手戻りを防ぐ
- MVPでも省略してはいけない非機能の最低ラインを固定する

## MVPとは何か

検証したい仮説を1つに絞り、それを最小のコストで現場検証できる範囲。デモや試作品ではなく、**対象業務で実際に使われて価値仮説を検証できるもの**。仮説が複数あるならMVPが複数あるか、仮説の絞り込み不足。

## MVPに含める条件

- 本質課題（problem_statement）の解決に直結する
- 対象利用者の主要業務シナリオ1本を最初から最後まで通せる
- 成功指標の測定に必要（測れないMVPは検証できない）
- これが無いと現場が業務で使えない（並行手作業が増えるだけになる）

## MVPから外す条件

- 発生頻度が低い例外ケース（当面は人間運用で回せる）
- 「あると便利」だが本質課題の解決に寄与しない
- 利用者が限定的で優先度の低い部門・シナリオ
- 技術的に未確定要素が大きく、MVP検証と切り離せる

外した項目は non_scope.md / 将来拡張範囲に理由付きで記録する（黙って落とさない）。

## PoCでよい条件

- 技術的実現可能性そのものが未検証（精度・性能・接続可否）
- 失敗の可能性が高く、失敗コストを最小にしたい
- 本番データ・本番権限なしで検証できる

PoCの場合は開発ドキュメント体系のPOCセット（`../../templates/development/sets/poc.md`）に接続し、Go/No-go基準を事前定義する。

## 商用化前提にすべき条件

- 検証したい仮説が業務価値（技術でなく）で、技術は枯れている
- 導入後すぐに業務依存が生まれる（止まると業務が止まる）
- 顧客が本番利用を前提に予算・体制を組んでいる

商用化前提なら、MVPでも認証認可・監視・再実行性・テストを省略しない（`../../.claude/rules/engineering-guardrails.md`）。

## 初期リリース範囲

- MVP合格後、最初に本番投入する範囲。MVPと同一とは限らない
- 対象利用者・対象データ・対象業務の範囲を明記する
- 並行運用（旧手順との併走）期間と終了条件を決める

## 将来拡張範囲

- MVP検証で得たい学びと、それにより判断する拡張項目を対にする
- 「データ蓄積Nヶ月後に再判断」など判断時期を付ける
- 拡張時に作り直しにならないための設計上の逃げ道はTech Leadへ引き継ぐ

## やらないことリスト

- non_scope.md に「やらないこと / 理由 / 再検討条件」の3点セットで記録する
- 顧客と合意した証跡（会議日・合意者）を残す
- Handoff時に実装チームへも共有する（実装側の善意の追加実装を防ぐ）

## 技術負債を避ける考え方

- MVPの「速さ」は機能を削って出す。品質を削って出さない
- 使い捨て前提のコードは「使い捨てる計画」（廃棄条件・時期）とセットでのみ許容する
- スキーマ・API契約など変更コストが高い部分は、MVPでも将来拡張を見て設計する（判断はTech Lead）

## 後回しにしてはいけない非機能要件

- 認証認可・権限制御（後付けは作り直しに近い）
- 秘密情報の管理（接続情報のハードコードをMVPでも許さない）
- 監視・失敗通知（気づけない障害は現場の信頼を一撃で失う）
- 再実行性・冪等性（データ処理を含む場合）
- 最低限の自動テスト（受入条件を検証できる範囲）

## セキュリティ・運用・品質の最低ライン

| 領域 | MVPでの最低ライン | 確定Role |
|---|---|---|
| セキュリティ | 権限制御・秘密管理・監査要否の判断が済んでいる | Security / Governance Engineer |
| 運用 | 失敗の検知手段と再実行手順があり、運用者が実施できる | SRE / Platform Engineer |
| データ品質 | 主要データの検証ルールと異常時の隔離・通知がある | Data Engineer |
| テスト | 受入条件が検証方法とセットで定義され、実施されている | QA Engineer |

## MVPスコープ判断チェックリスト

- [ ] 検証仮説が1つに絞れている
- [ ] MVPで解く課題がproblem_statementと一致している
- [ ] 含める/含めない/将来拡張が3区分で明文化されている
- [ ] 成功条件・受入条件が測定/検証可能
- [ ] 上記の非機能最低ラインが計画に入っている
- [ ] 現場の並行運用負荷が見積もられている
- [ ] 顧客の予算・期間制約に収まる見込みがある（超える場合は選択肢を提示）

## 例

サンプルは顧客情報を含まない共有fixtureだけを使う。Local `output/` の過去案件を共有Coreの正本として参照しない。
